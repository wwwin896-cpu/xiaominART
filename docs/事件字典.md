# 埋点事件字典

> 2026-10-07（T-02）建立。此前页面使用了 20+ 种 `data-event` 事件名，但客户端与服务端各有一层只含 6 个事件的白名单，绝大多数事件被静默丢弃，行为数据为空。现将两端白名单扩为全量，本文为唯一字典。
>
> **改动规则**：新增事件时，① 页面加 `data-event="xxx"`；② `src/scripts/cloud-forms.ts` 的 `TRACKED_EVENTS` 加同名项；③ `functions/api/event.ts` 的 `ALLOWED_EVENTS` 加同名项；④ 本文登记。三处缺一，事件依然会被丢弃或丢失语义。

## 上报链路

```
用户点击 [data-event] → Layout.astro 监听 → CustomEvent('xiaominart:event')
→ trackEvent()（客户端 TRACKED_EVENTS 过滤 + 会话内去重）
→ POST /api/event → 服务端 ALLOWED_EVENTS 过滤 → events 表
```

> **2026-10-09 补录说明**：上表后 5 项由 P0-03 / P1-02 / P0-04 三个工单引入，
> 上线时**只写了 `dispatchEvent`、漏登两端白名单**，因此被静默丢弃（与 `consultation_step`
> 同类问题）。已同步补入 `TRACKED_EVENTS` 与 `ALLOWED_EVENTS`。
>
> **同时修复**：`Layout.astro` 的 `[data-event]` 监听由「加载时逐个绑定」改为
> **document 级事件委托** —— 原写法对组件动态插入的节点（搜索结果项、选礼器选项卡等）
> 完全无效，属于埋点全空且无报错的高隐蔽缺陷。


> **2026-10-14 补录说明**：上表末尾 4 项为「作品编码 + 二维码扫码验真」上线时引入
> （`/verify/{编码}` 公开档案页）。已在本表、`src/scripts/cloud-forms.ts` 的
> `TRACKED_EVENTS`、`functions/api/event.ts` 的 `ALLOWED_EVENTS` 三处同步登记 ——
> 该功能此前已两次出现「只写 dispatchEvent、漏登白名单导致埋点被静默丢弃」的事故，
> 新增事件一律三处同改。
>
> ⚠️ 二维码由 `src/lib/qr.ts` 纯前端零依赖生成（**不调用任何外部二维码 API**，
> 避免把「客户扫了什么码」泄露给第三方），SVG 于构建期直接写进 HTML，零运行时请求。
> 生成正确性已用**独立解码器 jsQR** 做 6/6 round-trip 交叉验证（含中文与带参长 URL）。
>
> ⚠️ 微信生态硬限制：微信内打开的网页**无法一键跳转关注公众号**，关注段只能用
> 「长按识别二维码」引导；`src/data/site.ts` 的 `mpName` / `mpQr` 留空时，
> 关注段会自动隐藏并降级为个人微信，不会出现空二维码或死链。

> **2026-10-14 档案页改版（结论优先）**：业主反馈「用户停留时间短，只关心是不是正品」，
> 页面结构由「结论 → 证据 → 多段解释」压缩为「结论 + 实拍 → 下一步」。
> 删除了「如何核对三步」「编码怎么读」两段解释，「查另一件作品」入口也一并移除
> （客户手里只有一件，查别的没有意义）。
>
> 对应事件：新增 `archive_browse_click` / `archive_stories_click` / `archive_share_click`；
> `archive_query_click` / `archive_follow_click` 仍在白名单保留在册 ——
> **已上线的旧页面可能仍在发这两个事件，删白名单会造成埋点被静默丢弃**，
> 这是本仓库踩过多次的同类事故，故只增不删。
>
> ⚠️ 同时修复一处隐患：原埋点靠 `document.querySelector('.qr-cap')` 取作品编码，
> 改版后该元素被删，选择器会静默返回 null、导致**所有埋点丢失 code 归属且不报错**。
> 已改为由 Layout 的 `bodyData` prop 把编码写到 `<body data-archive-code>`，
> 不再依赖 DOM 里恰好存在某个元素。
