## 二、本批唯一真实待修项：③ Cookie 同意横幅

### 为什么必须做

- 隐私政策**第四条已声明**「我们可能使用 Cookies 及同类技术」；
- 但站上**没有任何同意入口** —— 有声明而无同意机制，是**合规缺口**；
- 百度统计（`hm.baidu.com`）属**非必要 Cookie**，PIPL 第 13/14 条要求取得**单独同意**。

### 关键设计：默认不统计，而非「加载后再屏蔽」

这是本次实现的核心决策。**反面做法**是：照常加载统计脚本，用户拒绝后再
「补一个删除 Cookie 的调用」 —— 那时**脚本已经执行、请求已经发出**，
数据已经落到第三方，合规上不成立。

**本批做法**：统计脚本在用户点「同意」前**根本不注入 DOM**。

三道闸门：

1. `CookieConsent.astro` 的 `is:inline` 脚本**同步执行**（在 `<head>` 里、
   任何 defer 脚本之前），把 `localStorage['xiaominart-consent'] === 'accept'`
   写入 `window.__xmConsent`；
2. `Layout.astro` 的统计注入块**读这个值**，`if(consent)load();` —— 不满足就
   完全不创建 `<script>` 标签；
3. 点「同意并启用」时，调用 `window.__xmLoadAnalytics()` **即时补加载**，
   无需刷新页面。

### 改动文件

| 文件 | 改动 |
| ---- | ---- |
| `src/components/CookieConsent.astro` | **新建**。固定底栏横幅；同意/拒绝两按钮同为 `btn` 级（**不做暗黑模式** —— 这是合规硬要求）；选择存 `localStorage` 键 `xiaominart-consent`（**不设 Cookie 本身**，避免「用 Cookie 记 Cookie」）；实测横幅高度写入 `--consent-h` |
| `src/layouts/Layout.astro` | import + 挂载 `<CookieConsent />`；GA4 / Umami / Clarity / 百度统计**四段注入整体重构**为「读 `__xmConsent` → 同意后 `load()`」；暴露 `window.__xmLoadAnalytics`；新增 `body.consent-open .mobile-shopping-bar { bottom: var(--consent-h, 168px); }` 避免移动底栏被横幅遮挡 |
| `src/pages/privacy/index.astro` | 新增「重新选择」入口：清除 localStorage 后刷新（**PIPL 第 15 条：同意可以撤回**） |

### 边界处理

- **无 JS 环境**：横幅是 `hidden` 属性控制的静态块，脚本不跑就不显示，
  不阻塞内容（统计也不加载，符合「默认不统计」）；
- **隐私模式 / localStorage 被禁**：读写都包在 `try/catch` 内，异常时
  视为「未同意」→ 不统计；隐私政策页的「重新选择」若失败会提示
  「浏览器阻止了本地存储，请在浏览器设置中清除本网站数据」；
- **移动端底栏冲突**：底栏与横幅都 `position: fixed; bottom: 0`，
  故实测横幅高度并顶起底栏，`resize` 时重算（写死高度在文案换行/字号
  变化时会失准）。

### 排障过程（已按受限网络 skill 的完整流程走完）

1. 读取本会话代理端口：**60259**（环境变量 `http_proxy` / `https_proxy`）；
2. `curl -x http://127.0.0.1:60259 https://github.com/` → **000**；
3. 扫描**全部**本地监听端口对 `github.com` 的连通性 → **无任何一个通**；
4. 对照实验：同一端口 `https://api.github.com/rate_limit` → **200**
   （即网络本身正常，是 `github.com` 被单独拦截）；
5. 显式指定代理 + `HTTP/1.1` + `postBuffer=500MB`，**重试 20 次** →
   全部 `CONNECT tunnel failed, response 502` 或 `schannel: server closed abruptly`；
6. 直连（清除代理）→ 同样失败。

**判定：符合「真僵局」特征** —— `api.github.com` 可达但 `github.com` 不可达，
说明本会话代理只放行 API 域名，而 git 走的是 `github.com` 的 smart HTTP 通道。
**继续重试无意义，故停止。**

### 恢复方式（三选一，均无需改动代码）

1. **等网络恢复后**在仓库目录执行 `git push origin main` —— 最省事；
2. 让助手在**新的会话**里重试（代理端口每次会话轮换，新端口可能放行）；
3. 把本地 `ef559d5` 的改动（3 个文件）拷到有网络的机器上提交。

> 验证推送成功：`git rev-parse main` 与 `git ls-remote origin main` 两个 SHA 一致。
> 推送后 CI 会自动跑 `check` + `check:sitemap` 门禁，Cloudflare Pages 约 40–60 秒生效。

### 推送后的线上验证清单

1. 无 `xiaominart-consent` 记录时打开首页 → **不应有 `hm.baidu.com` 请求**
