# 小民艺术两份营销指令合并后的开发意见

## 结论先行

两份附件的品牌方向一致：小民艺术应从“高冷艺术 / 只做定制咨询”转向“营造静气生活的家居物件、人情伴手礼和企业文化礼品”。

但现有网站仍是 Astro 静态展示站，核心 CTA 还是定制咨询，项目明确没有购物车、库存、订单、支付或现货销售能力。因此建议采用“先验证转化、再接入交易”的两阶段路线，而不是直接把假价格、假库存和假订单流程上线。

## 一、现状与指令的关键差距

### 1. 业务模型需要先定稿

现有项目在 `README.md` 中明确不包含 checkout、payment、cart、stock、order；商品和价格也没有真实数据源。两份指令要求用户完成浏览、比较、加心愿单、结算、支付、订单成功和电子贺卡，这已经是电商系统，不是普通文案和页面改版。

**意见：**

- 如果近期仍以“定制项目沟通”为主，先做“礼品目录 + 送礼指南 + 咨询转化”版本，不展示可直接付款承诺。
- 如果确实要 C 端直接下单，必须新增商品、SKU、库存、订单、支付、物流、退款和通知系统，并由负责人确认真实业务规则后再开发。

### 2. 价格区间存在冲突，不能自行猜测

营销方案给出的价格是：入门款 ¥500–1,500、心意款 ¥1,500–3,000、珍藏款 ¥3,000 以上；直接执行 Prompt 给出的价格是：入门款 ¥100–300、心意款 ¥300–500、珍藏款 ¥800 以上。

当前代码中的价格参考又是另一套定制预算，且页面明确“不是现货商品价格”。

**意见：**

在负责人确认前，不应把任意一套价格发布成商品价格。开发上应先建立可配置的价格层级数据，价格、交付时间、包装费和运费都由内容数据或 CMS 管理，而不是散落在页面文案里。

### 3. 商品数量要求不一致

营销方案要求每个送礼场景推荐 3–5 款；直接 Prompt 要求每个场景推荐 35 款。以当前没有真实商品目录的状态，直接填充 35 款会制造虚假商品内容。

**意见：**

- MVP 阶段：每个场景上线 3–5 个经过确认的商品/品类方向。
- 扩展阶段：有真实商品、图片、包装、价格和交期后，再扩充到每场景 35 款。
- 若 35 款是硬性目标，应先完成商品资料采集和内容授权，不应使用概念案例冒充商品。

### 4. 文案和视觉方向可以立即执行

以下内容不依赖支付系统，可以作为第一批开发：

- Hero 改为生活化、送礼导向表达。
- 首屏增加“送礼指南”快捷入口。
- 导航改为“送礼指南 / 生活场景 / 静气生活 / 企业伴手礼”主路径。
- 场景页、送礼指南、静气生活栏目和企业伴手礼页。
- 米白、原木、墨色、自然光、生活实景、克制动效。
- 商品/案例详情页加入寓意、包装、发货说明和 FAQ 模块。

## 二、建议的可执行产品路线

## Phase 0：业务确认门（开发前必须完成）

负责人只需要确认以下 8 项，确认后即可进入开发：

1. 当前阶段是“咨询转化”还是“直接下单支付”。
2. 采用哪一套 C 端价格区间，或提供真实 SKU 价格表。
3. 首批真实商品/品类、库存状态、图片授权和包装图片。
4. 各商品的预计发货时间、配送范围、运费规则和售后规则。
5. 礼品包装是否收费、是否所有商品支持、包装选项有哪些。
6. 贺卡字数限制、可否预览、是否允许修改。
7. 支付渠道、开票规则、退款规则和订单通知方式。
8. B 端询盘的接收邮箱/后台、文件上传存储和 24 小时联系承诺是否真实成立。

未确认的字段在网站上应显示“咨询确认”，不要伪造确定值。

## Phase 1：无支付的 C 端转化 MVP

目标是先让普通消费者明确“能送什么、送给谁、多少钱、何时能到、怎么包装”，并把兴趣转为可追踪咨询。

### 1. 首页

建议 Hero 首选文案：

> 一份带着书香静气的心意
> 家居摆件 · 人情好礼

备选文案保留在文案包中，后续通过数据配置或 A/B 测试切换。

首屏下方增加三个入口：

- 送礼指南
- 按生活场景看看
- 不知道怎么选？获取送礼建议

首屏场景图需要真实生活素材：书房、茶室、客厅玄关、礼品包装和交付实景；在真实素材到位前使用“方向参考”标识，不应伪称实拍。

### 2. 导航

建议新的一级信息架构：

1. 送礼指南
2. 生活场景
3. 静气生活
4. 企业伴手礼

Logo 返回首页；页脚保留关于我们、常见问题、联系方式和定制咨询。

“生活场景”二级分类：

- 书房静气
- 客厅雅致
- 茶室禅意
- 送礼心意
- 企业伴手礼

这会替代当前 `src/data/content.ts` 中只有五项通用导航的结构，导航数据应改为支持 `children` 的类型，而不是继续追加硬编码链接。

### 3. 送礼指南页

建议路由：`/gift-guide/`，英文路由：`/en/gift-guide/`。

页面结构：

1. 顶部按送礼场景筛选：乔迁、开业、生日、节日、感谢恩师/朋友。
2. 预算筛选：预算区间必须由负责人确认后上线；未确认时展示“预算待确认”或先使用咨询筛选。
3. 商品/品类卡片：寓意、适合对象、包装选项、预计发货时间、价格/价格区间。
4. 心愿单：先做浏览器本地收藏，避免第一阶段引入账号系统。
5. 礼品包装说明与送礼 FAQ。
6. 统一 CTA：查看详情、加入心愿单、咨询送礼建议。

第一阶段不应出现“加入购物车 / 立即付款”，除非支付和订单后端已完成。

### 4. 商品/礼品详情页

建议建立产品数据模型，至少包括：

- slug、中文/英文标题
- 产品类型与送礼场景
- 寓意和适合对象
- 真实图片、包装图片及授权状态
- 价格或价格区间
- 包装选项
- 发货时间
- 配送范围
- 售后规则
- FAQ
- 分享文案

交互优先级：

1. 包装选项展示
2. 贺卡文字输入与本地预览
3. 心愿单
4. 分享心意
5. 送礼咨询

电子贺卡发送、订单关联和收礼人信息收集可在支付链路完成后接入；MVP 先支持生成可分享预览，不承诺已发送。

### 5. C 端送礼 FAQ

两份指令列出的 7 个问题应放在详情页和送礼指南页，不要只放在全局 FAQ：退换货、包装贺卡、发货时效、发票、直寄去小票、说明卡、加急处理。

回答必须使用负责人确认的业务规则。当前项目没有真实售后、物流和发票配置，开发阶段只能先建立内容结构，不能发布确定承诺。

## Phase 2：真实交易链路

只有 Phase 0 的业务数据和支付规则确认后再做。

### 必要模块

- 商品与 SKU 管理
- 库存或可售状态
- 购物车
- 结算页
- 商品金额、包装费、运费和总价拆分
- 直寄收礼人并去除价格小票的显性勾选
- 贺卡内容预览
- 支付
- 订单成功页
- 订单查询和通知
- 退款/售后
- 电子贺卡生成与分享

这部分不能依靠 Astro 静态 HTML 表单完成。需要后端 API、数据库、支付服务、邮件/消息服务及安全的订单状态校验。

## Phase 3：B 端企业伴手礼

当前 `src/pages/business-custom/index.astro` 使用 `mailto:` 提交，无法满足“文件上传、后台接收、24 小时内联系、不拉起邮件客户端”的要求。

建议拆为独立路由 `/business-gifts/`，与大型企业空间定制 `/business-custom/` 区分。

### 页面模块

- 企业伴手礼定位与场景：客户答谢、员工福利、会议、开业、节日慰问。
- 三档方案：轻量款 50 份起、定制款 100 份起、专属款 200 份起；上线前确认这些起订量真实有效。
- 3 个案例模板，模拟案例必须明确标注“示例”，不能伪造客户反馈。
- B 端 FAQ 至少 8 条。
- 表单字段：预算、数量、用途多选、期望交付时间、Logo/VI、参考图。
- 提交成功页：明确说明收到需求和后续联系时限；只有确有人工响应能力时才写“24 小时”。

技术上需要：表单 API、文件上传限制、对象存储、邮件或 CRM 通知、垃圾提交防护和隐私说明。

## 三、技术实现建议

### 1. 保留 Astro，但补齐数据层

现有 Astro + TypeScript 适合 SEO 和内容页，可继续使用。建议：

- 静态生成首页、送礼指南、场景页和内容页。
- 产品数据先放在结构化 TypeScript 数据层或 Sanity；不要把商品属性散落到 Astro 模板。
- 当进入交易阶段，再增加服务端 API 或独立电商后端。
- 所有页面使用统一的产品类型、场景类型、价格类型和 FAQ 类型。

### 2. 心愿单分两步

- MVP：`localStorage` 保存匿名用户收藏，支持跨页面查看和移除。
- 交易阶段：登录后同步云端心愿单，支持多设备和下单关联。

### 3. 图片与内容真实性

当前代码仍有概念案例和“案例资料整理中”等内容。新定位强调真实送礼场景，因此：

- 未授权图片必须标注“参考方向”或不公开。
- 未确认客户评价不能写成真实买家反馈。
- 商品包装、发货时间、价格和售后必须来自负责人确认的数据。
- 所有内容字段增加 `status: draft | example | approved`，生产环境只展示 approved，或明确展示 example。

### 4. 性能与视觉

继续保留当前 Astro 的静态输出和克制动效。新增图片时：

- 使用响应式图片和明确的尺寸属性。
- 首屏只加载必要场景图。
- 避免把 35 个商品的原图全部首屏加载。
- 保留米白、原木、墨色和衬线排版，不引入高饱和电商促销风格。

## 四、建议的开发顺序与验收

### 第一批可立即开发

1. 更新品牌文案和 Hero。
2. 新导航和生活场景架构。
3. `/gift-guide/` 与 `/en/gift-guide/` 页面骨架。
4. 结构化商品/品类数据模型。
5. 预算和场景筛选组件。
6. 商品详情页的寓意、包装、发货和 FAQ 模块。
7. 浏览器本地心愿单。
8. C 端送礼 FAQ。
9. `静气生活` 栏目规划和首期 3 篇文章结构。
10. B 端伴手礼页面和表单原型，先不接真实上传接口。

### 第二批再开发

1. 真实商品图片、价格、包装、交期导入。
2. B 端表单 API 和文件上传。
3. 分享卡片和电子贺卡预览。
4. 购物车、结算、支付、订单和通知。
5. 真实 UGC 与企业案例。
6. CMS 内容运营和 SEO 批量管理。

### 验收必须覆盖

- 首页 3 秒内能理解“可选礼品/送礼指南”定位。
- 能从导航进入送礼指南和生活场景。
- 能按场景和预算筛选；预算值与真实数据一致。
- 商品详情页能看到寓意、包装、时效和 FAQ。
- 心愿单可添加、查看、移除，刷新后仍保留。
- 如果未接支付，不显示“立即付款”假入口。
- 如果已接支付，结算页金额、包装费、运费透明，直寄去小票是显性选项。
- B 端文件上传、通知和成功页均真实可用。
- 中英文关键路径和移动端菜单同步。
- `npm run check`、`npm run build`、关键路由和移动端无横向溢出。

## 五、我的开发建议

我建议批准以下范围作为第一轮正式开发：

- 采用新品牌定位和生活化 Hero。
- 先上线送礼指南、生活场景、静气生活和企业伴手礼信息架构。
- 用 3–5 个真实或明确标注为示例的品类/商品做 MVP，不直接承诺每场景 35 款。
- 先实现本地心愿单、详情页送礼信息和 FAQ。
- 暂不上线支付按钮，直到价格、库存、物流、售后和支付服务确认。
- 在负责人确认商品资料后，再进入购物车、结算和支付开发。

这样可以快速验证“送礼”定位和用户路径，同时避免把现有的概念案例、定制预算或占位数据误包装成可购买商品。
